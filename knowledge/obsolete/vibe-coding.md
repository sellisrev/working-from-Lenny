# Obsolete advice: Vibe coding and PM prototyping with AI

## "Vibe coding is controversial; you can't ship anything substantial without understanding the code"

- **Claim**: Vibe coding produces code you don't understand, so it works only for tiny experiments. Once the codebase grows, you hit a wall and can't change anything.
- **Originally said by**: Michael Truell (Cursor co-founder), [The rise of Cursor](https://www.youtube.com/watch?v=En5cSXgGvZM), 2025-05-01.
- **Why obsolete**: By April 2026, Intercom (a public-company-stage SaaS, not a hobbyist) reported [2x merged-PR throughput in 9 months with 100% of engineers, designers, PMs, and TPMs shipping via Claude Code](https://www.youtube.com/watch?v=BRDKft0-dUU). The "wall" is real but moves outward with model-quality jumps (Sonnet 4.6 / Opus 4.6 in Nov-Dec 2025) and platform features (skills, hooks, Outcomes, telemetry). The 2025-05 claim implicitly assumed the human had to understand each line; production teams now treat code review + rubrics + tests as the harness, not in-flight comprehension.
- **Where it may still apply**:
  - Without skills/hooks/telemetry harnesses (i.e., a solo dev or small team without quality gates), vibe-coded codebases past ~10k LOC do still hit the wall Truell described.
  - For non-trivial state machines, distributed systems, or anything requiring formal verification (security-critical, regulated software, etc.), the "you have to understand it" rule still applies — Anthropic itself attributes the April 2026 Claude Code source code leak partly to AI-mediated PR review going wrong.
  - Truell's framing is still current Cursor product strategy: they're investing in "continued control over all the details when [users] don't really understand the code."
- **Replaced by**: see [Current consensus on Vibe coding and PM prototyping with AI](../topics/vibe-coding.md#current-consensus).
- **Confidence in retirement**: high — multi-source recency, including Anthropic's own product team and a non-AI-native production company (Intercom).

## "AI prototyping is for product managers (the rest of the team will use real tools)"

- **Claim**: Implied by early framings (Lenny's January 2025 "guide to AI prototyping for product managers" framing), positioning AI prototyping as a PM workflow distinct from how engineers and designers work.
- **Originally said by**: Lenny Rachitsky, [a-guide-to-ai-prototyping-for-product-managers.md], early 2025; reinforced by the "PM second brain" framing.
- **Why obsolete**: By June 2025, Colin Matthews's update [explicitly addresses team workflows](https://www.lennysnewsletter.com/p/how-to-get-your-entire-team-prototyping-with-ai) including engineering and design integration. By April 2026 (Intercom), the working assumption is that all functions ship code via the same tools.
- **Where it may still apply**:
  - At companies where engineering hasn't adopted AI tools, PM-led prototyping workflows are still meaningfully different from engineering workflows. The PM-isolated framing is correct for organizations that haven't crossed the AI-adoption threshold.
- **Replaced by**: "Get your entire team prototyping with AI" framing; see [Current consensus](../topics/vibe-coding.md#current-consensus).
- **Confidence in retirement**: high.

## "Engineers must read every line of code they ship"

- **Claim**: Implicit pre-AI assumption baked into careful-engineering frameworks (Shape Up, code review norms, etc.).
- **Originally said by**: Pre-2025 corpus throughout; not a single source.
- **Why obsolete**: At Intercom and Anthropic in 2026, a substantial fraction of merged code was generated by AI and reviewed at the diff/test/rubric level rather than line-by-line. Brian Scanlan (Intercom): "imagination is now the barrier not the tool." Cat Wu (Anthropic): "as code becomes much cheaper to write, the thing that becomes more valuable is deciding what to write."
- **Where it may still apply**:
  - Security-critical and compliance-bound code (Anthropic's own leak supports this).
  - Junior development as a learning tool: there is no consensus replacement for the apprenticeship-by-careful-implementation that the old model produced. Truell and Cat Wu both flag this as an open question, not a solved one.
  - Code that will be operated and maintained by a different person/team than wrote it; review burden may shift but doesn't disappear.
- **Replaced by**: "test+rubric+telemetry harness" model; see [Current consensus](../topics/vibe-coding.md#current-consensus).
- **Confidence in retirement**: medium — the principle has shifted but the "how do you train juniors" question is unresolved.
